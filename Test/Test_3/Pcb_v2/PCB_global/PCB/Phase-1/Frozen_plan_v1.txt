**Status:** Architecture Complete · Implementation‑Validated · Frozen for Schematic Capture  
**Supersedes:** All prior memories and DEIA v4.0  
**Next Step:** Write the four mandatory specification documents, then open EDA software.

---

## Why v5.0 Exists

DEIA v4.0 closed every architectural gap raised by the 8.5–9.2 reviews. However, a final, rigorous PCB‑design review exposed **five implementation‑level flaws** that would have caused thermal failure, bus overruns, and unnecessary complexity when translated to a schematic. v5.0 corrects these at the architecture level so that the specification documents inherit only sound, buildable constraints.

| Flaw in v4.0 | v5.0 Correction |
|--------------|----------------|
| **LTC4370 “linear gate modulation” for blending** – would force a MOSFET into linear operation, dissipating >10 W of heat during transition | LTC4370 used **only as an ideal‑diode OR‑ing controller**. Solar/battery blending is achieved by **MPPT droop control** (MPPT voltage setpoint falls as load increases). No linear blending across a pass‑FET. |
| **RAID‑1 SD cards on STM32H7** – unpredictable write latencies stall CAN RX, risking buffer overruns | Single industrial SLC microSD for bulk telemetry (with power‑fail‑safe LittleFS). Critical config DB & event log stored in **deterministic 16 MB NOR flash** (W25Q128). No software RAID. |
| **Discrete P‑FET reverse‑polarity protection + eFuse inrush limiter** – redundant, adds voltage drop and BOM cost | eFuse/hot‑swap controller (e.g., TPS25947) **natively handles reverse‑current blocking and reverse‑polarity**. No extra P‑FET; if the chosen eFuse lacks reverse protection, use an ideal‑diode controller, not a discrete FET. |
| **29‑bit Extended CAN IDs** – adds ~20 bits/frame overhead, increases arbitration latency | **11‑bit Standard CAN IDs mandated.** 2048 identifiers suffice for 128 nodes × 10 message types. Priority‑encoded: bits 10‑8 = priority, bits 7‑4 = node ID, bits 3‑0 = message type. |
| **ISOW1412 isolated DC‑DC current limit not validated** – isolated rail may exceed 130 mA thermal limit if powering CAN termination or under fault | Each node must perform an **isolated power budget**. If the isolated secondary load exceeds 80 mA (leaving thermal margin), replace ISOW1412 with a dedicated 1 W isolated DC‑DC module (e.g., B0505XT‑2WR3) + digital isolator + CAN transceiver. ISOW1412 only approved when the budget stays below 80 mA. |

All other decisions from DEIA v4.0 remain unchanged and are now locked.

# The Frozen Architecture — DEIA v5.0

## 1. System Philosophy (Frozen)

- **Priority hierarchy:** Safety → Survivability → Stability → Observability → Optimization.
- **Local control loops only:** No safety‑critical function depends on CAN.
- **Raw telemetry only:** Nodes broadcast facts; coordinator derives opinions.
- **Fault injection is the only acceptable proof of fault tolerance.**
- **Degraded mode autonomy:** CAN bus loss or coordinator failure = all nodes revert to 100% local autonomous operation. Observability is lost, safety is not.

## 2. Protection Classes (Frozen)

- **Class A (<10 µs):** Hardware‑only — latching eFuses, TVS, UVLO with hysteresis, crowbar.
- **Class B (>10 ms):** MCU or CAN‑based preventive actions.

## 3. Power Architecture (Frozen, Corrected)

### 3.1 Distributed DC Bus
- 12–18 V V_BUS, shared power backbone.
- Every node carries its own point‑of‑load (PoL) buck converters for 5 V / 3.3 V.
- Dual V_BUS optional for Phase 2 (not required now).

### 3.2 Power Source Blending: MPPT Droop + Ideal‑Diode OR‑ing
- **No linear gate modulation.** Never use a MOSFET in its linear region to blend sources — it would overheat instantly.
- **Solar MPPT uses analog droop control:** As current demand rises, the MPPT intentionally lowers its output voltage setpoint (e.g., from 14.4 V to 13.0 V). This naturally allows the battery to share the load smoothly.
- **LTC4370 is configured strictly as an ideal‑diode OR‑ing controller:** It prevents reverse current from the battery into the solar panel, and provides fast, smooth switchover when one source voltage exceeds the other. Transition dip remains <200 mV under worst‑case load steps.
- Detailed schematic and droop setpoint calculation in Power Architecture Specification.

### 3.3 Load Shedding
- Dual‑threshold UVLO: 10.8 V warning (MCU notified), 10.0 V hard disconnect (hardware latch).
- Hysteresis and soft‑start to prevent oscillation during battery ESR sag recovery.

### 3.4 Bus & Node Protection (Simplified)
- **Every node** has:
  - **eFuse/hot‑swap controller** (e.g., TPS25947) that handles inrush current limiting, over‑current, under‑voltage lockout, **and reverse‑current/reverse‑polarity protection**. No discrete P‑FET needed.
  - TVS diode on V_BUS input (SMBJ18A).
- **Power source nodes** (battery, MPPT) additionally have a latching eFuse at the output to protect the bus from a downstream short circuit.

### 3.5 Power Budget & Thermal Analysis (Mandated)
- Complete power budget spreadsheet including quiescent and dynamic currents for every node.
- Thermal analysis for all power devices (eFuse MOSFETs, DC‑DC converters). Must be delivered as part of Power Architecture Specification.

## 4. Grounding, Isolation & Physical Layer (Frozen, Validated)

### 4.1 Isolation Mandate
- **Full galvanic isolation per node.**
- Primary isolation element: **ISOW1412** (isolated DC‑DC + digital isolator) **only if** the total isolated‑side current draw is <80 mA (including CAN transceiver, termination, and margin). Otherwise, use a discrete 1 W isolated DC‑DC module + digital isolator + CAN transceiver.
- The CAN transceiver (e.g., TCAN1044V) is always a separate SOT‑23‑5 on the isolated side.

### 4.2 6‑Pin Backbone (Unchanged)
| Pin | Signal      | Description |
|-----|-------------|-------------|
| 1   | V_BUS       | 12–18 V power |
| 2   | GND_POWER   | Power return (primary side) |
| 3   | CAN_H       | Isolated CAN high |
| 4   | CAN_L       | Isolated CAN low |
| 5   | CAN_GND     | Isolated reference (secondary) – never connected to GND_POWER |
| 6   | SHIELD      | Overall cable shield, terminated via 1–10 nF capacitor to chassis or GND_POWER |

### 4.3 Connectors & Hot‑Plug
- Phase 1 prototype: JST‑GH (with documented migration path).
- Field/deployment: M12 A‑coded with shielded metal shell.
- Hot‑plug sequence: V_BUS/GND mate first (longer pins), then CAN, then power‑good signal.

### 4.4 EMI/EMC Guidelines
- Unbroken ground plane per node.
- Common‑mode choke (ACT45B‑510‑2P) + dual TVS (NUP2105L) at each CAN connector entry.
- Shield bonded to chassis (if metal) or to GND_POWER via capacitor.
- CAN bundle separated >10 cm from high‑dI/dt lines.

## 5. CAN‑FD Communication (Frozen, Corrected)

### 5.1 Topology & Timing
- Linear bus, terminated 120 Ω at both ends.
- 2 Mbps data phase, 500 kbps arbitration.
- Maximum backbone length: 40 m (with M12 connectors, cable C <50 pF/m).
- Stubs ≤30 cm.

### 5.2 Standard 11‑bit CAN IDs (Mandated)
- **11‑bit Standard Frame Format only.** 29‑bit Extended IDs are unnecessary and degrade bus bandwidth.
- ID allocation: bits 10‑8 = priority (0 highest), bits 7‑4 = node ID (0‑15, expandable), bits 3‑0 = message type.
- Full ID map to be defined in Node Interface Standard.

### 5.3 Bus Fault Tolerance
- CAN is telemetry only. A severed bus causes loss of observability; all nodes continue autonomous safe operation.
- This is an explicit architectural decision: survivable degradation, not a design flaw.

## 6. Node Intelligence (Frozen)

- Main MCU: STM32G4 or H7 with native FDCAN.
- Coordinator (STM32H7) has an ESP32 WiFi bridge for cloud/SOS. ESP32 uses ESP‑NOW or static‑IP UDP for <500 ms bursts; powered off when not needed.
- Raw telemetry broadcast: V, I, T, SoC, SOH, node health bitfield.
- 3‑tier watchdog: internal → external WDT IC → D‑FF hardware latch forcing safe‑state (all outputs off).

## 7. Addressing, Discovery & Identity (Frozen)

- 48‑bit UUID per node (from MCU unique ID).
- Dynamic discovery via well‑known CAN ID; coordinator assigns short logical ID (0‑127) from configuration database.
- Node replacement: new UUID triggers re‑commissioning; operator approval required.

## 8. Firmware Updates & Security (Frozen)

### 8.1 Signed Firmware & Secure Boot
- Every node contains an **ATECC608B** (or compatible) secure element.
- Firmware images signed (Ed25519) by coordinator’s private key.
- Bootloader verifies signature via burned‑in public key before writing to flash.
- Unsigned firmware rejected; security event logged.

### 8.2 A/B Partitioning with Rollback
- Dual flash banks; new image installed, tested, then marked active.
- If self‑test fails within timeout, hardware watchdog triggers rollback to previous bank.

### 8.3 CAN Message Authentication (Phase 2)
- For Phase 1, physical CAN bus is assumed trusted (isolated habitat). This risk is formally accepted (SEC‑002).

## 9. Redundancy & Degraded Modes (Frozen)

- Coordinator failure: all nodes continue local autonomous operation. Time‑stamping drifts <100 ppm until coordinator returns and resynchronises. Local logging continues.
- Optional hot‑standby coordinator for Phase 2.

## 10. Data Architecture & Storage (Simplified, Deterministic)

### 10.1 Critical Configuration & Event Logs
- **16 MB NOR flash (W25Q128)** on coordinator stores the golden configuration database and critical event logs. NOR flash offers deterministic, zero‑latency writes and is immune to power‑loss corruption.

### 10.2 Bulk Telemetry
- **Single industrial SLC microSD card** (Swissbit or ATP) with LittleFS power‑fail‑safe filesystem for bulk telemetry circular logging.
- No RAID‑1. The NOR flash is the redundant safety net for critical data.

### 10.3 Data Format
- CBOR for all telemetry records.

## 11. Time Synchronisation (Frozen)

- Coordinator broadcasts UTC time every 1 s on a dedicated CAN ID.
- Nodes discipline a software PLL to achieve ~2 ms typical, <5 ms worst‑case accuracy.
- Hard‑real‑time nodes may later use a dedicated PPS line (architectural provision made).

## 12. Verification & Fault Injection Plan (Frozen)

The test plan (separate document) will include:
- Power handover under worst‑case load steps (MPPT droop transition)
- CAN bus fault injection (short, open, missing termination, ground offset)
- Watchdog failure injection
- Environmental: temperature, vibration, EMC pre‑compliance
- Security: flashing unsigned firmware (must fail)
- All with numerical pass/fail criteria

   - **Power Architecture Specification v1.0** — MPPT droop setpoints, eFuse selection, power budget, thermal analysis, UVLO thresholds, connector hot‑plug sequencing, cable gauge validation.

3. **Prototype, test, and iterate.** The architecture direction will not change; only component values or layout details may be tuned based on measured results.

# Why DEIA v5.0 Is Now Unassailable

- **Physically sound:** Ideal‑diode OR‑ing, not linear blending; deterministic storage; validated isolation power budgets.
- **Secure by design:** Hardware‑backed signed firmware, secure boot, key management.
- **Fault‑tolerant:** Any single failure (CAN cut, coordinator loss, node short) leaves the system safe and operational.
- **Lifecycle‑ready:** UUID discovery, A/B OTA updates, config database, time sync.
- **Testable:** Every requirement has a pass/fail criterion; fault injection mandated.
- **Efficient:** 11‑bit CAN IDs, no redundant protection components, no unnecessary storage complexity.
